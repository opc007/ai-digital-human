# 阶段 0～1 任务拆解

> 配套文档：`更合理的开发思路`（对话结论）+ `AI数字人SaaS平台-开发文档.md`（蓝图）  
> 目标：用约 **4 周** 完成「效果预研 → 稳定播报机」  
> 通过闸门后再进入阶段 2（半自动互动）

---

## 0. 假设与约定

### 0.1 团队（默认 2 人，可一人兼职）

| 角色 | 代号 | 主责 |
|------|------|------|
| 算法 / 多媒体 | **A** | 形象生成、口型、动作拼接、FFmpeg 推流、GPU |
| 全栈 / 工程 | **B** | 目录脚手架、配置、TTS 接入、进程守护、日志、简单 Web/CLI |

1 人全包时：按「先 A 再 B」串行，周期约 ×1.5～2。

### 0.2 环境基线

| 项 | 最低要求 |
|----|----------|
| GPU | 24G 显存（RTX 4090 / A10 等）；口型与生成可分时复用 |
| 系统 | Windows 或 Ubuntu 22.04（推流建议 Linux 更稳） |
| 软件 | CUDA、FFmpeg、Python 3.10+、Git |
| 账号 | DeepSeek（阶段 2 再用）、MiniMax 或本地 TTS、直播平台**测试号**推流码 |

### 0.3 本阶段成功标准（总闸门）

阶段 0 + 1 **全部**满足才进入阶段 2：

- [ ] 有可对外展示的 3～5 分钟样片（阶段 0）
- [ ] 脚本驱动数字人说话并 RTMP 推到真实测试号
- [ ] 连续直播 **≥ 1 小时**（目标 2 小时）无不可恢复故障
- [ ] 记录单小时成本、显存峰值、断流次数
- [ ] 仓库内 `README` 能让同事按步骤复现

### 0.4 明确不做（阶段 0～1）

- 用户注册 / 多租户 / 支付  
- LLM 对话、弹幕抓取  
- Kafka、K8s、微服务拆分  
- 20 个完整动作库（本阶段 **5～10 个** 即可）  
- Electron / 完整 Vue 后台

## 1. 推荐目录结构（阶段 0～1 落盘）

从第 1 周起按此建仓，后续阶段只增量，不推倒重来。

```text
ai-digital-human/
├── README.md                 # 环境、一键命令、闸门清单
├── docs/
│   ├── 阶段0-1任务拆解.md     # 本文
│   └── MVP技术规格-精简版.md
├── configs/
│   ├── default.yaml          # 全局默认
│   └── rooms/
│       └── demo.yaml         # 演示房间：文案、推流、素材路径
├── data/
│   ├── avatars/
│   │   └── demo/
│   │       ├── source/       # 原图
│   │       ├── actions/      # wave.mp4, idle.mp4 ...
│   │       └── meta.json     # 动作列表与时长
│   ├── audio/                # TTS 缓存
│   └── output/               # 合成视频 / 录像
├── scripts/
│   ├── 00_check_env.py       # 环境自检
│   ├── 01_gen_actions.md     # ComfyUI/Wan 操作说明（可逐步脚本化）
│   ├── 02_tts_batch.py       # 文案 → 音频
│   ├── 03_lipsync.py         # 音频 + 参考视频 → 口型视频
│   ├── 04_compose_playlist.py# 按脚本拼接动作/口型段
│   ├── 05_push_rtmp.sh       # 或 .ps1：FFmpeg 推流
│   └── 06_run_broadcast.py   # 一键：读配置 → TTS → 口型 → 推流
├── src/
│   └── broadcast/            # 阶段 1 起的薄封装（可先空）
│       ├── __init__.py
│       ├── config.py
│       ├── tts.py
│       ├── lipsync.py
│       ├── playlist.py
│       └── stream.py
├── tools/
│   └── watchdog.py           # 进程守护 / 推流检测（阶段 1 后半）
├── requirements.txt

```

**原则：** 阶段 0 以 `scripts/` + 手工为主；阶段 1 把稳定路径收进 `src/broadcast/` 与 `06_run_broadcast.py`。

## 3. 第 1 周：阶段 0 效果预研

### 3.1 目标

用**最少链路**证明：这张脸 + 这套口型 + 推流画质，团队/客户愿意继续投入。

### 3.2 按天任务

| 天 | 角色 | 任务 | 产出 |
|----|------|------|------|
| D1 | A+B | 定 1 张测试人脸（正脸、高清、光照均匀）；建仓与目录；装 CUDA/FFmpeg/Python | 仓库 + 原图入库 |
| D1 | B | 写 `scripts/00_check_env.py`：检测 GPU、ffmpeg、磁盘 | 自检通过日志 |
| D2 | A | ComfyUI + Wan2.2（或现有图生视频）跑通 **1 个** 动作（如 idle 或 wave） | 1 段 3～5s 视频 |
| D3 | A | 再生成 **2～4 个** 动作（wave / nod / idle 优先） | 共 3～5 段素材 |
| D3 | B | 申请/配置 TTS；写最小脚本：一段固定中文 → wav/pcm | `data/audio/demo.wav` |
| D4 | A | MuseTalk（或阶段选型模型）：参考视频 + demo 音频 → 口型视频 | 1 段可播放 mp4 |
| D5 | A+B | FFmpeg 本地播放/虚拟推流；剪 3～5 分钟「静音展示 + 说话展示」样片 | `data/output/sample_w1.mp4` |
| D5 | 全员 | **评审会**（见 3.3 闸门） | 书面结论：继续 / 换模型 / 暂停 |

### 3.3 阶段 0 闸门（D5 评审）

每人独立打分（1～5），平均 **≥ 3.5** 且无「一票否决」项：

| 项 | 否决条件 |
|----|----------|
| 身份一致性 | 明显换人、脸崩 |
| 口型 | 严重不同步、牙齿/下巴撕裂感强 |
| 可用性 | 抖/糊/分辨率无法接受上播 |
| 主观意愿 | 「不愿意给客户看样片」 |

**不过关：** 不进入 W2 工程化；用 3～5 天换参考图、分辨率、口型模型或降低预期（纯播报、少互动）。

### 3.4 W1 验收清单

- [ ] `data/avatars/demo/actions/` 至少 3 个 mp4  
- [ ] 1 段完整口型成片  
- [ ] 样片路径与评审记录写在 `README` 或 `docs/review-w1.md`  
- [ ] 决策：进入阶段 1 / 延期 / 止损

## 4. 第 2 周：文案 → 音频 → 口型（批处理闭环）

### 4.1 目标

任意改 `demo.yaml` 里几段文案，能批量产出可播放片段，**无需每次手点 ComfyUI 全流程**（动作库可仍半手工）。

### 4.2 按天任务

| 天 | 角色 | 任务 | 产出 |
|----|------|------|------|
| D1 | B | `configs/default.yaml` + `rooms/demo.yaml`（文案列表、音色、路径） | 配置可加载 |
| D1 | B | `src/broadcast/config.py` 读 YAML；`.env.example` | 配置模块 |
| D2 | B | `tts.py` + `02_tts_batch.py`：多句文案 → 多文件音频；失败重试 | 批量 wav |
| D2 | A | 固定口型参数（分辨率、fps、参考视频选择策略）写进配置 | `lipsync` 默认参数 |
| D3 | A | `03_lipsync.py`：输入音频 + action/idle 参考视频 → 输出 mp4；命令行可跑 | 单句可复现 |
| D4 | A+B | 批处理 5～10 句；统一 25fps、分辨率（如 960×540 或 720p） | `data/output/clips/` |
| D4 | B | 简单日志（时间、句序、耗时、成功/失败） | 控制台或 `logs/` |
| D5 | A | 补齐动作至 **5～10 个**；写 `meta.json`（name, file, duration_ms, category） | 小动作库 |
| D5 | 全员 | 走通：改文案 → 一键批处理 → 抽查 3 段质量 | W2 演示 |

### 4.3 `demo.yaml` 最小字段（示例）

```yaml
room_id: demo
avatar_dir: data/avatars/demo
tts:
  provider: minimax   # 或 local
  voice_id: your_voice
script:
  - id: open
    text: "大家好，欢迎来到直播间。"
    action: wave
  - id: intro
    text: "今天给大家分享三个小技巧。"
    action: nod
  - id: close
    text: "感谢支持，我们下期见。"
    action: thanks_wave
stream:
  # W3 再填
  rtmp_url: ""
  rtmp_key: ""
```

### 4.4 W2 闸门

- [ ] 修改 script 后，**一条命令**生成全部 clips（允许口型较慢）  
- [ ] 单句失败不拖垮整批（跳过 + 日志）  
- [ ] 素材与配置分离，换一张脸只换 `avatar_dir`  
- [ ] 记录：平均每句 TTS 耗时、口型耗时、显存峰值

## 5. 第 3 周：拼接 + RTMP 推流

### 5.1 目标

按脚本顺序播放：idle 垫片 → 说话段 → idle；推出到**真实测试号**。

### 5.2 按天任务

| 天 | 角色 | 任务 | 产出 |
|----|------|------|------|
| D1 | A | `04_compose_playlist.py`：按 script 顺序生成播放列表（文件列表或 concat demuxer） | playlist.txt / 长视频 |
| D1 | A | 段间策略：硬切 or 短 fade（200～300ms）；无任务时循环 idle | 不黑屏 |
| D2 | B | `05_push_rtmp`：FFmpeg 参数模板（ultrafast/zerolatency、AAC、码率 3～5Mbps 可配） | 可推本地/测试 |
| D2 | B | 推流码只放 `.env` / 本机配置，不进 Git | 安全约定 |
| D3 | A+B | 平台测试号首播：观察延迟、卡顿、画质、声画同步 | 问题清单 |
| D4 | B | `06_run_broadcast.py`：读配置 →（可选跳过已生成）→ 推流；CLI 参数 `--skip-tts` 等 | 一键开播脚本 |
| D4 | A | 断流手动重推流程写进 README | 运维说明 |
| D5 | 全员 | 完整彩排 30～60 分钟；修阻塞 Bug | 能「准直播」 |

### 5.3 FFmpeg 推流注意点（实现时对照）

- 输入帧率稳定，避免无 `-re` 导致瞬间灌爆  
- 视频 `libx264` + `tune zerolatency`（或硬件编码若已验证）  
- 音频采样率与 AAC 兼容（常见 44.1k/48k）  
- 断线：进程退出码检测 → 指数退避重连（W4 完善）  

### 5.4 W3 闸门

- [ ] 测试号可搜到/可看（按平台规则）  
- [ ] 声画基本同步，无长时间黑屏  
- [ ] 一键脚本从「已有 clips」到推流 ≤ 几条命令  
- [ ] 已知问题列表（延迟、码率、重连）进入 W4

## 6. 第 4 周：稳定性、成本、闸门评审

### 6.1 目标

达到「播报机」可内测标准；输出数据决定是否进入阶段 2。

### 6.2 按天任务

| 天 | 角色 | 任务 | 产出 |
|----|------|------|------|
| D1 | B | `tools/watchdog.py`：拉起推流进程；崩溃重启；连续失败告警（日志/微信机器人任选） | 守护可用 |
| D1 | A | 显存：推流中是否误占 GPU；口型与推流分时则保证推流阶段可释放 | 显存策略说明 |
| D2 | A+B | **压力：连续 1 小时**直播；记录断流、重启、音画问题 | `docs/burnin-1h.md` |
| D3 | 同上 | 条件允许则 **2 小时**；修复 D2 问题 | burnin 报告更新 |
| D4 | B | 成本表：GPU 时费、TTS 字符费、带宽（若有）；折算 元/小时 | `docs/cost-w4.md` |
| D4 | B | README 复现步骤：从 clone 到开播（给「另一个人」试做） | 可用性验证 |
| D5 | 全员 | **阶段 1 总闸门评审**（见 6.3） | Go / No-Go 阶段 2 |

### 6.3 阶段 1 总闸门

| 编号 | 标准 | 必过 |
|------|------|------|
| G1 | 真实测试号推流成功 | 是 |
| G2 | 连续直播 ≥ 1h，不可恢复故障 = 0 | 是 |
| G3 | 断流可自动或一键恢复 | 是 |
| G4 | 单小时成本有数据，且业务可接受 | 是 |
| G5 | 非作者按 README 能在 1 天内复现环境并推流 | 尽量 |
| G6 | 样片/直播观感仍达阶段 0 标准（无退化） | 是 |

**Go：** 进入阶段 2（半自动互动：手动输入 + LLM + 队列）。  
**No-Go：** 只修稳定/画质，不开启 LLM 与 Web 互动（避免复杂度叠加）。

## 9. 风险与缓冲

| 风险 | 缓冲 |
|------|------|
| Wan/口型环境装不顺 | W1 预留 D2～D3 只打仗环境；用现成短视频先测口型 |
| TTS 审核/开通慢 | 本地 Fish-Speech / edge 临时音色打通流程 |
| 平台推流失败 | 先推 nginx-rtmp / 本地 mediakit 验证管道，再上平台 |
| 单人开发 | W1～W2 合并为 3 周效果+批处理，W3～W4 推流稳定共 3 周 |
